# Contributing to Quantum Dot Games projects

Thanks for your interest in contributing! Bug reports, ideas, documentation improvements, code, artwork, and other useful changes are welcome, depending on the project.

The aim is to keep contributing straightforward. You are free to use your own tools and workflow, including AI assistance. What matters is that a contribution is understandable, appropriate for the project, and meets its quality requirements.

## Before you start

Please follow our [Code of Conduct](CODE_OF_CONDUCT.md) when participating in project discussions and reviews.

- Read the project's README, licence, and any project-specific contribution guidance. Local guidance takes precedence over these shared defaults.
- Check existing issues and pull requests to see whether the same problem or idea is already being discussed.
- For small, self-contained fixes, feel free to open a pull request without asking first.
- For substantial features, major redesigns, or changes likely to require ongoing maintenance, opening an issue or discussion first is encouraged. This is not permission to experiment; it simply helps avoid duplicated effort and work that may not fit the project's direction.

## Reporting bugs and suggesting features

Use the repository's GitHub Issues page to report bugs or suggest improvements. A clear description of the issue, relevant version or environment, and reproduction steps (where possible) are helpful. Screenshots or examples are welcome when they add useful context.

You do not need to supply a fix to report a problem. Likewise, an issue is not required before submitting a straightforward fix.

For potentially sensitive security vulnerabilities, follow [the security policy](SECURITY.md) rather than posting exploitable details publicly.

## Pull requests

Please keep a pull request focused on one coherent change where practical. Before submitting:

- Make sure the change works as intended and follows the project's existing conventions.
- Perform sensible checks for the type of change, such as tests, builds, visual inspection, or compatibility checks, where applicable.
- Avoid introducing unrelated changes, unnecessary dependencies, or unlicensed third-party materials.
- Explain the outcome and why it matters, briefly summarise the key changes, and describe what you verified. If something could not be tested, just say so.
- Link a related issue if there is one. Screenshots are especially helpful for visual changes.

You do not need to follow any particular development toolchain beyond the project's actual requirements. AI-generated and AI-assisted contributions are welcome; disclosure of the tools or models used is not required. Contributors should review the changes they submit and be able to explain what those changes do.

## Quality and project-specific requirements

Contributions are reviewed based on their suitability, clarity, maintainability, compatibility, and any technical standards defined by the project. Some repositories may set additional requirements around supported platforms, APIs, dependencies, performance, or backwards compatibility. For example, a change to a public API may require compatibility checks or migration notes that an internal bug fix would not. Projects involving artwork, 3D assets, or other non-code material may also have their own requirements.

Testing should be proportionate to the change. A typo correction does not need the same verification as a new subsystem.

## Review and acceptance

Pull requests may be reviewed with automated or AI-assisted tools, but the project maintainers decide what is accepted. A technically correct change may still be declined if it does not suit the project's scope, direction, or maintenance needs. Submitting a contribution does not guarantee a merge or a response within a specific timeframe.

If changes are needed, maintainers may request revisions, make adjustments themselves, or close the pull request. Contributors are not obligated to provide ongoing work or support after submitting a contribution.

## Licensing, rights, and credit

Only submit work you have the rights to contribute. Do not include proprietary code, paid assets, or other third-party material unless its licence and redistribution terms permit their inclusion in this project. Clearly identify relevant third-party material and applicable terms.

Unless a separate agreement is explicitly made, contributions are provided under the licence or licences stated in the relevant repository. Contributors retain ownership of their original work while granting the rights applicable under those terms. If licensing is unclear, particularly for assets, ask before submitting substantial material.

GitHub's normal commit and contributor attribution is generally how contributions are recognised. Accepted contributions do not automatically grant maintainer status, project ownership, repository permissions, or decision-making authority. No separate contributor list is promised.

Thanks for helping improve the projects, whether through a small correction or a larger contribution.
